## 1. DB 直モード (読むのは DB・書くのは API)

いまはすべてプリザンターの API を通している。API に無いこと (集計・「以外」「より大きい」などの条件・リンク先の名前での並び) はコネクターが行を読んでメモリで補っているので、
件数の多いサイトが苦手で、QueryField も使えない。プリザンターの DB に届く環境では、読み出しだけ DB に流せるようにする。

- **デザイナの設定は今と同じにする。** 表名は接続文字列の `Sites` の別名・列名は今と同じ (`ClassA` などは DB の列名でもある)・定義は今のメタ情報のファイル。違いは接続文字列だけにする
- 書き込みは API のまま (DB に直接書くと、`Items` の索引・`Links`・履歴・計算式・サーバースクリプト・通知が抜ける)
- API だけの形は残す (DB に届かない環境用。同じデザインをそのまま使える)

### 案

- SQL をパースしない。SQL の先頭に別名の定義を足して、元の DB アクセスに流す (WITH の名前は同じ名前の表より優先される)。本体が組んだ SQL も QueryField の SQL も同じ扱い

  ```sql
  WITH "Projects" AS (SELECT ... FROM "Results" WHERE "SiteId" = 1200),
       "Customers" AS (SELECT ... FROM "Results" WHERE "SiteId" = 1300)
  (元の SQL をそのまま)
  ```

- 値を API と同じ見え方に揃える変換 (空の日付 → null・日時のタイムゾーン・空の文字・チェックの null) は、その WITH の中の SELECT でメタ情報から組み立てる
- 設定は、プリザンターのデータソースに「読み出しに使う DB のデータソース名」を足す。振り分けは入口の 1 か所 (select → DB / それ以外 → API)

### 先に実物で確かめること

- DB の中の空の値の入り方・日時の持ち方 (UTC か)
- 複数の列で作るタイトル (`Items` との結合)・`Comments` の形
- プリザンターが要求する PostgreSQL の版 (12 より前は WITH の中身が外の条件と合わせて最適化されない)
- 本体だけでプリザンターの DB を読んで、どこまで素で動くか (最初の一歩)

### 注意点

- 元の SQL が WITH で始まるときは、定義をつなげる処理が要る
- クエリに `"Results"` と直接書けば `Sites` に無いサイトの行も読める (絞り込みは強制にならない)
- DB の接続は読み取り専用の利用者にする前提 (クエリで update を書かれるとプリザンターの処理を通らずに書ける)
- 確認には `Live/LiveDifferentialTest` (同じ条件を 2 つの道で実行して突き合わせる) を「API の道と DB の道」に使う

## 2. SQL Server・MySQL のプリザンター対応

プリザンターは SQL Server・PostgreSQL・MySQL に対応している。このコネクターを確かめたのは PostgreSQL のプリザンターだけ。

- API を通す今の形: 文字の比較 (大文字・小文字・全角半角・照合) とメモリでの並びが、DB の照合によっては View の道とメモリの道で変わりうる。メモリでの評価は PostgreSQL のプリザンターに合わせてある
- DB 直モード: `DataSourceType` を実物の DB に合わせて書くことになる (今は一律 `PostgreSQL`)。値を揃える式は DB ごとに書き分ける。WITH は 3 つとも使える (MySQL は 8.0 以降)
- 順番の案: DB 直モードを PostgreSQL で先に作って突き合わせを通し、SQL Server と MySQL は式の書き分けと環境の用意を後から足す
