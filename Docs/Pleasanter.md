# プリザンター コネクター

プリザンター (Implem.Pleasanter) のサイト (記録テーブル・期限付きテーブル) を、Codeer.LowCode.Blazor のデータソースとして扱うためのライブラリです。
モジュールをプリザンターのサイトに結び付けると、いつもの一覧・検索・詳細・保存の操作がそのままプリザンターの読み書きになります。
URL・JSON・SQL を手で書く必要はありません。

- 一覧・検索・件数・作成・更新・削除: プリザンターの API (`api/items/...`)
- 集計・LinkField 越しの項目での検索と並べ替え: コネクターがプリザンターから読んだレコードで行う
- ExecuteSqlField: プリザンターの拡張 SQL の呼び出し
- 選択肢・リンクの取り込み (デザイナ)・プリザンターのログインを使うシングルサインオンの部品
- 認証: 連携用の利用者の API キー

プリザンター 1.5.9.1 (DB は PostgreSQL) で動作を確かめています。

## 使い方の流れ

1. プリザンターで連携用の利用者と API キーを用意する
2. アプリとデザイナにプリザンターのデータソースを書く (使うサイトを並べる)
3. アプリとデザイナにコネクターを組み込む (1 行ずつ)
4. デザイナでメタ情報を取り込み、DB のテーブルと同じ手順でサイトからモジュールを作る

## 1. プリザンター側の準備

- **連携用の利用者と API キー**: アプリがつなぐための利用者を作り、その利用者で API キーを作ります (プリザンターの「API の設定」)
- **アクセス権を絞る**: 連携用の利用者には、アプリから扱うサイトだけを読み書きできる権限を付けます
- **https**: プリザンターを `https://` で公開します (API キーを要求ごとに送るため、コネクターは `localhost` 以外への `http://` の接続を受け付けません)

プリザンターで読み書きする主体は、この連携用の利用者です。アプリにログインした利用者ごとの権限は、モジュールの権限設定で決めます。

## 2. データソース

アプリの `appsettings.json` とデザイナの設定の DataSources に、DB と同じ並びで書きます。`ConnectionString` を `Provider=Pleasanter;` で始めたものがプリザンターのデータソースです。

```json
{
  "DataSources": [
    {
      "Name": "Pleasanter",
      "DataSourceType": "PostgreSQL",
      "ConnectionString": "Provider=Pleasanter;Url=https://example.com/pleasanter/;ApiKey=xxxxxxxx;Sites=Customers:1300,Projects:1200"
    }
  ]
}
```

`DataSourceType` は `PostgreSQL` にします (プリザンター用の値はありません。コネクターが PostgreSQL の書き方で組まれた問い合わせを読み替えます)。

| キー | 必須 | 内容 |
|---|---|---|
| `Provider` | ○ | `Pleasanter` |
| `Url` | ○ | プリザンターのアプリのルート (仮想ディレクトリまで)。`https://` で始める。`http://` は `localhost`・`127.0.0.1` のときだけ使えます。リダイレクトには従わないので、転送された先の最終の URL を書きます |
| `ApiKey` | ○ | 連携用の利用者の API キー |
| `Sites` | ○ | 使うサイトを `表名:サイトID` で並べる。**表名はここで付ける名前**で、モジュールの DbTable になります (英数字と `_`)。ここに無いサイトは読み書きしません |
| `MaxRows` | | コネクターが全部読むときに受け取る行の上限。既定 10000。超えると (黙って切り捨てずに) エラーになります |
| `TimeoutSeconds` | | 1 回の要求のタイムアウト (秒)。既定 100 |
| `EmptyDate` | | プリザンターが空の日付として返す値。既定 `1899-12-30`。通常は書きません (General.json の MinTime の値ではありません) |

- 表名をサイト ID と分けてあるので、検証と本番でサイト ID が違っても、接続文字列の `Sites` を変えるだけでデザインはそのまま使えます
- 書き方の誤りは既定値にせずエラーにします
- API キーは DB の接続文字列と同じ扱いにしてください (デザインのファイルやリポジトリに入れない。運用環境では環境変数やシークレットストアから渡す)

## 3. 組み込み

| プロジェクト | パッケージ |
|---|---|
| アプリ (サーバー) | `Codeer.LowCode.Blazor.Connectors.Pleasanter.Server` |
| デザイナ | `Codeer.LowCode.Blazor.Connectors.Pleasanter.Designer` |

### アプリ (サーバー)

`ModuleDataIO` に渡す `IDbAccessor` を `PleasanterDbAccessor` で包みます。

```csharp
using Codeer.LowCode.Blazor.Connectors.Pleasanter.Server;

DbAccess = new DbAccessor(SystemConfig.Instance.DataSources);
var pleasanter = new PleasanterDbAccessor(DbAccess, PleasanterConnection.FromDataSources(SystemConfig.Instance.DataSources),
    PleasanterMetadataFile.FromDeployedDesign(SystemConfig.Instance.DesignFileDirectory));
ModuleDataIO = new CustomizedModuleDataIO(Design.DesignData, this, pleasanter, TemporaryFileManager);
```

3 つ目の引数で、サイトの定義 (メタ情報) を配られたデザインから読みます (下の「メタ情報はファイルから読む」)。

### デザイナ

`IDbAccessorFactory` の実装で `IDbAccessor` を包みます。

```csharp
using Codeer.LowCode.Blazor.Connectors.Pleasanter.Designer;

public class DbAccessorFactory : IDbAccessorFactory
{
    public IDbAccessor Create(DataSource[] dataSources)
        => PleasanterDesignerInitializer.CreateDbAccessor(new DbAccessor(dataSources), dataSources);
}
```

デザイナのアプリの `OnStartup` に 2 行足します。

```csharp
protected override void OnStartup(StartupEventArgs e)
{
    PleasanterDesignerInitializer.Initialize(DesignerEnvironment);   //base.OnStartup より前
    base.OnStartup(e);
    PleasanterDesignerInitializer.Setup(DesignerEnvironment);        //base.OnStartup の後
}
```

プリザンター以外のデータソースは、包んだ `DbAccessor` がこれまでどおり処理します。

組み込んだアプリとデザイナの見本は [Source/Example](../Source/Example) にあります ([Example.md](Example.md))。

### メタ情報はファイルから読む

デザイナとアプリは、プリザンターのサイトの定義 (メタ情報) をファイル `pleasanter.<データソース名>.metadata.json` から読みます。
ファイルはデザインのプロジェクトの**サーバー専用ファイル** (ServerFiles) に置かれ、デザインと一緒にアプリへ配られます (画面には送られません)。
デザイナもアプリも、動いている間にプリザンターへサイトの設定を取りに行くことはありません。

- **取り込み・更新**: デザイナのメニュー **Tools > プリザンターのメタ情報を更新**。`Sites` に並べたサイトの定義をプリザンターから取り直してファイルに保存します。
  最初の 1 回と、プリザンター側で項目・選択肢・リンクを変えたとき、`Sites` を変えたときに実行してください。ファイルが無いうちは、プリザンターの表はデザイナに出ません
- **アプリへの反映**: 更新したら、デザインをいつもどおりデプロイします。アプリは新しいデザインに入ったファイルを次の要求から使います (再起動は要りません)
- **中身**: サイトごとの表名・サイト ID・種類・キーの列と、列の名前・種類・読み取り専用かどうか・空を持てるか・項目名・選択肢・リンク先です。接続先や API キーは入りません。
  デザインのファイルと一緒にリポジトリへ入れておけば、プリザンターに接続できない環境でもデザインできます
- サイト ID は、アプリでは接続文字列の `Sites` のものを使います (検証で書き出したファイルを、サイト ID の違う本番でもそのまま使えます)
- モジュールが使う表がファイルに無いと、アプリはエラーになります (メタ情報を更新してデプロイし直すよう案内が出ます)
- 更新に失敗したときは、前のファイルがそのまま残ります

## 4. モジュールを作る

デザイナのデータソースに、`Sites` に並べたサイトが DB のテーブルと同じように並びます。テーブルからモジュールを作るのと同じ手順で作れます。

| モジュールの設定 | プリザンターでは |
|---|---|
| DataSourceName | プリザンターのデータソース名 |
| DbTable | `Sites` で付けた表名 (プリザンターのサイト名ではありません) |
| フィールドの DbColumn | プリザンターの内部の列名 (`Title`・`ClassA`・`NumA`・`DateA`・`DescriptionA`・`CheckA`・`Status` など)。画面の項目名ではありません |
| Id フィールド | DbColumn は記録テーブルなら `ResultId`、期限付きテーブルなら `IssueId` |

- Id はプリザンターが採番します。Id フィールドを手入力にしないでください
- 拡張の項目 (`ClassA` など) は、サイトのエディタか一覧に出している項目だけが列になります。プリザンターの API がそれ以外の項目の値を返さないためです
- 使う列だけをフィールドにしてください。フィールドにしていない列は読みも書きもしません
- 一覧には表示件数を設定してください。件数を絞らない読み出しは `MaxRows` を超えるとエラーになります

### コメント

列 `Comments` でプリザンターのレコードのコメントを扱えます (TextField)。

- 読むと、プリザンターが返すコメントの一覧がそのまま (JSON の文字で) 入ります。新しい順で、コメントが無ければ `[]` です
- 文字を入れて保存すると、その文字がコメント 1 件として足されます。前のコメントは変わりません (消す・直すことはできません)。空のまま保存しても何も起こりません
- 読み込んだレコードでは、フィールドにコメントの一覧の JSON が入っています。その中身を書き換えて保存すると、書き換えた文字全体が 1 件のコメントとして足されます (変えずに保存すれば何も送りません)。
  既存のレコードの画面では表示専用にし、入力させるのは新規作成の画面 (最初のコメント) にしてください
- 検索の条件・並べ替え・集計には使えません (エラーになります)

### 列の種類

| プリザンターの項目 | 列の型 | フィールド |
|---|---|---|
| `Title`・`Body`・分類 (`ClassA`…)・説明 (`DescriptionA`…) | 文字列 | TextField (`Body`・説明は複数行) |
| 数値 (`NumA`…)・`Status`・`Manager`・`Owner`・`WorkValue`・`ProgressRate` など | 数値 | NumberField (表示の書式 `Format` を付けると、`8.0000` のような小数の桁が整います) |
| 日付 (`DateA`…) で書式が年月日のもの | 日付 | DateField |
| 日付で時刻を持つもの・`StartTime`・`CompletionTime`・`CreatedTime`・`UpdatedTime` | 日時 | DateTimeField (SaveAsUtc はオフのまま) |
| チェック (`CheckA`…) | 真偽 | BooleanField |

- **日時は時差を持たない値として読み書きします。** プリザンターの日時は、API キーの利用者のタイムゾーンでの値のまま読み書きされます。DateTimeField の SaveAsUtc はオンにしないでください (ずれます)
- 年月日の日付の項目に時刻の入った値がある (API などで時刻つきで書かれた) ときも、日付として読み、検索でもその日として扱います。
  ただし並べ替えはプリザンターが行うので、同じ日の中の順は入っている時刻の順になります
- 数値の項目は、プリザンターの項目の設定で空を許していなければ、空にすると 0 になります
- チェックの項目は空を持ちません (空はチェックなし)
- `Manager`・`Owner`・`Creator`・`Updator` はプリザンターの利用者の ID です (名前にはなりません)
- プリザンターで入力必須の項目も、列としては空を許す形で見えます。必須かどうかは保存のときにプリザンターが確かめます。画面で先に止めたいときは、フィールドを必須にしてください

### 選択肢

メタ情報の更新のときに、項目の選択肢 (値と表示の並び) も取り込みます。

- 画面では、選択肢を CLB の Enum の定義に写し、フィールドを Enum の選択 (SelectField) にします。保存するのは値、画面に出るのは表示です
- 分類の項目 (`ClassA` など) は、値をそのまま Enum のメンバーにします
- 数値の項目 (`Status` の状況など) は、Enum の値の型を数値にして (`"ValueType": "Number"`)、メンバーの名前を表示、値を数字にします。画面には「受注」のような表示が出て、プリザンターには数字が保存されます。検索の条件にも使えます
- 選択肢の中身を画面のたびにプリザンターから読むことはしません。プリザンターで選択肢を変えたら、メタ情報を更新して Enum の定義を直してください
- 利用者・組織から選ぶ項目の選択肢は取り込みません (値は ID のままです)

### 読み取り専用の列

キー (`ResultId` / `IssueId`)・`Ver`・`Creator`・`Updator`・`CreatedTime`・`UpdatedTime`・`RemainingWorkValue` (残作業量。作業量と進捗率からプリザンターが計算する) は読み取り専用の列です。

- レイアウトで表示専用 (IsViewOnly) にして置きます。値は保存のあとで読み直すと出ます
- 値を入れて保存するとエラーになります
- フィールドの名前を `CreatedAt` / `UpdatedAt` / `Creator` / `Updater` にしないでください。CLB のシステムフィールドになり、保存のたびに値を書こうとしてエラーになります (`CreatedTime` の列なら `Created` などの名前にします)

### ほかのサイトとの関係

プリザンターで別のサイトへのリンクにした項目 (選択肢に `[[サイトID]]` を書いた分類の項目) は、メタ情報にリンク先が入ります。

- 相手のサイトも `Sites` に並べ、相手のモジュールを作って LinkField で結びます。項目に入るのは相手のレコードの ID です。一覧・詳細で相手の項目 (会社名など) を表示できます
- 親子 (案件と作業など) は DB の親子と同じ作りです。子のモジュールに親を指す LinkField を置き、親のモジュールに子の一覧 (ListField) を置いて、子の LinkField = 親の Id で絞ります。
  親と子を 1 つの画面で作成・編集できます
- 結べるのは同じプリザンターのデータソースのサイト同士です。プリザンターのサイトと DB のテーブルは結合できません

例は Example の `Project` (案件。取引先へのリンクと作業の一覧) と `WorkTask` (作業) です。

### 楽観ロック

`UpdatedTime` の列に、`OptimisticLocking` のフィールド (版を上げない設定) を結びます。画面を開いたあとにほかの人がプリザンターで更新していれば、保存が止まります。
`Ver` は更新しても上がらないことがあるので、楽観ロックには使いません。動きは下の「保存」を読んでください。

## 動き

### 一覧・検索

モジュールの検索条件・並び・ページング・件数は、プリザンターの一覧の条件 (フィルタ・並び・ページ) になってプリザンターで実行されます。

使える検索条件:

- 比較 (等しい・等しくない・大小・範囲)・部分一致・空欄かどうか・候補のどれか (In)
- 条件の組み合わせ (かつ・または・否定)
- LinkField の値での検索 (例: 作業を案件で絞る)
- LinkField 越しの項目での検索 (例: 案件を取引先の会社名で絞る)
- 子の一覧の項目での検索
- LinkField 越しの項目での並べ替え

プリザンターのフィルタにそのまま書けない条件 (等しくない・否定・空でない・より大きい / より小さい・複数選択の項目の条件など) を含む検索は、
条件を広げてプリザンターから読み、コネクターが絞ります。この読み出しは `MaxRows` までです。件数の多い一覧では、等しい・以上・以下・部分一致・空欄の条件でも絞れるようにしてください。

- LinkField 越しの項目・子の一覧の項目での検索は、コネクターが先に相手のサイトを条件で読んで ID を集め、主のサイトを「集めた値のどれかに一致」で読みます
- LinkField 越しの項目・リンクの項目での並べ替えは、条件に合うレコードを全部読み (`MaxRows` まで)、コネクターが並べてページを切ります。
  空欄は昇順で文字なら先・数値と日付なら後、文字は文字コードの順で、プリザンターの画面の並びと違うことがあります
- ページをまたいでも順序が変わらないよう、並びの最後にキーの列が足されます
- 文字の比較: 等しいは大文字・小文字を区別し、部分一致は区別しません (PostgreSQL のプリザンターで確かめた動き)
- 検索の値が `Own` の文字の条件は、コネクターが読んだレコードで判定します (プリザンターは利用者の項目の `Own` を「API キーの利用者」に読み替えるため)。`Own` はいつも文字の `Own` として比べます

### 集計

集計 (件数・重複なしの件数・合計・平均・最小・最大を項目ごとにまとめる機能) は、プリザンターの API に集計が無いため、
**条件に合うレコードを全部読んでコネクターが計算します** (`MaxRows` まで。超えたらエラー)。条件・集計後の絞り込み・並び・上位の件数・LinkField 越しの項目の軸も使えます。

- 日付の項目を年・四半期 (年度の開始月つき)・月・週 (月曜始まり)・日・時でまとめる集計も使えます。日付の項目に時刻の入った値があっても、その日としてまとめます

例は Example の `AmountByCustomer` (案件の金額を取引先 × 区分で合計するクロス集計) です。

### 保存

| 操作 | プリザンターへの要求 |
|---|---|
| 新規 | レコードの作成。プリザンターが採番した ID が Id になる |
| 更新 | 変更したフィールドだけを更新する |
| 削除 | レコードの削除 |

- 更新・削除は、先にそのサイトにそのレコードがあるか (楽観ロックの条件も含めて) を確かめてから送ります
- 空にした項目は、文字は空・数値は空 (空を持てない項目は 0)・日付はプリザンターの空の日付・チェックはなしで送ります
- プリザンターの入力の検証で止められたときは、保存がエラーになります
- **プリザンターへの保存はレコード 1 件ごとに確定します。ロールバックはしません。** 同じ保存の中のほかの処理が失敗しても戻りません。
  親と子を一緒に保存する画面や、プリザンターと DB を一緒に書く画面は、途中まで保存された状態が起こりえます。そろっていないと困る組み合わせは、画面を分けてください
- 一括の追加は 1 件ずつ作ります。途中で失敗したときは、エラーのメッセージに作成済みの件数が入ります (作成済みのレコードは残ります)
- **楽観ロックは「先に確かめる」だけです。** 確かめてから書くまでのわずかな間に入った別の更新は防げません
- 書き込みを送ったあと応答を受け取れなかった場合は、実行されたかどうかが分かりません。コネクターはやり直さず (二重に作らないため)、`WriteResultUnknown` のエラーにします。プリザンター側で結果を確かめてください

### ExecuteSqlField (拡張 SQL)

ExecuteSqlField のコマンドの種類をストアドプロシージャにすると、プリザンターの拡張 SQL を呼べます。コマンドのテキストが拡張 SQL の名前 (`Name`) です。SQL 文は実行できません。

- プリザンターの `App_Data/Parameters/ExtendedSqls` に拡張 SQL を置き、API から使えるようにします (`"Api": true`)。連携用の利用者の API キーで呼びます
- 入力のパラメータの名前は、モジュールのフィールドの DbColumn と同じにします (一致しないパラメータは送られません)。その名前が拡張 SQL の中の `@名前` になります (プリザンターの表を持つモジュールでは列名なので `@ClassA` のようになります)。日付と日時は日時として渡ります。値の無いパラメータは渡せません (プリザンターがエラーにします)
- 結果は、拡張 SQL が返す最初の表の最初の行です。出力のパラメータには同じ名前の列の値が入ります。値を 1 つ返す呼び方 (Scalar) では先頭の列の値が戻り値です。更新の件数は分かりません (-1)
- 書き込みとして扱い、失敗してもやり直しません。拡張 SQL が無い・API から使えない・パラメータが足りない・SQL のエラーは、プリザンターがどれも同じ応答を返すので、
  `WriteResultUnknown` のエラーになります (メッセージに考えられる理由が入ります)。実行されたかどうかはプリザンター側で確かめてください

## プリザンターのログインを使うシングルサインオン

プリザンターにログインしているブラウザなら、アプリのログイン画面を出さずに同じ人としてアプリに入れるようにする部品です。
コネクターは、ブラウザが持つプリザンターの Cookie で本人を確かめるだけです。ログインの画面・Cookie の発行・利用者の表との突き合わせはアプリ (ホスト) が行います。

プリザンターに、ログイン中の本人を返す拡張 SQL (`ClbWhoAmI`。見本は [Source/Example/Pleasanter/ExtendedSqls/ClbWhoAmI.json](../Source/Example/Pleasanter/ExtendedSqls/ClbWhoAmI.json)) を置きます。

```csharp
var connection = PleasanterConnection.FromDataSources(SystemConfig.Instance.DataSources).First(e => e.Settings.Name == "Pleasanter");
var cookies = Request.Cookies.Select(e => new KeyValuePair<string, string>(e.Key, e.Value));
var result = await connection.VerifySessionAsync(cookies);
switch (result.Status)
{
    case PleasanterSessionStatus.Authenticated:     //result.Identity (TenantId / UserId / LoginId / Name) で利用者の行を引いてログインさせる
    case PleasanterSessionStatus.Unauthenticated:   //プリザンターでログインしていない
    case PleasanterSessionStatus.Failed:            //確かめられなかった (プリザンターに届かないなど)。result.Message はログ用
}
```

- プリザンターの認証の Cookie だけをプリザンターに送ります。API キーは送りません。Cookie はどこにも保存しません。1 回だけ送ります (やり直しません)
- 失敗しても例外を投げずに結果で返します
- ブラウザがプリザンターの Cookie をアプリにも送る必要があります。プリザンターとアプリを同じホスト名で動かします (ポートは違ってよい)
- **ログインのあとのデータの読み書きは連携用の利用者のままです。** 利用者本人のプリザンターの権限では読み書きしません。利用者ごとの権限は、モジュールの権限設定で決めます

組み込みの見本 (待ち画面・確かめ直し・ログアウト) は Example にあります ([Example.md](Example.md) の「SSO を有効にする」)。

## エラー

コネクターの失敗は `PleasanterException` で、`Kind` で種類が分かります。`StatusCode` に HTTP のステータス、`ApiStatusCode` にプリザンターの応答の StatusCode が入ります。API キーや接続文字列はメッセージに入りません。

| Kind | 内容 |
|---|---|
| `Authentication` | API キーが違う |
| `Forbidden` | 連携用の利用者に権限が無い |
| `NotFound` | サイト・レコードが無い |
| `InvalidRequest` | 入力・プリザンターの検証のエラー、`MaxRows` の超過 |
| `NotSupported` | 設定の誤り・コネクターが扱えない操作 (下の「制限」)・表にできないサイト (Wiki・フォルダ・サイト統合など) |
| `ServiceUnavailable` | プリザンター側・通信の障害、要求の回数の上限 |
| `WriteResultUnknown` | 書き込みを送ったが、実行されたかどうかが分からない |
| `Unknown` | 上のどれにも当たらない応答 |

読み出しは一時的な失敗 (混雑・障害・通信の失敗) を時間を置いて 3 回までやり直します。書き込みはやり直しません。

## 制限

### プリザンターの仕様によるもの

- プリザンターの API に集計は無いので、集計はコネクターがレコードを読んで行います (`MaxRows` まで)
- プリザンターの API は、エディタにも一覧にも出していない拡張の項目の値を返しません。その項目は列になりません
- 期限付きテーブルの残作業量 (`RemainingWorkValue`) は、プリザンターのフィルタに書けないため、条件はコネクターが読んだレコードで判定します

### コネクターがまだ対応していないもの

- 添付ファイル・画像・ロック・プロセス
- 利用者・組織の名前の表示 (ID のまま)
- Wiki・フォルダ・ダッシュボード・サイト統合のサイト
- 利用者本人の API キーでの接続
- サーバースクリプトの呼び出し

### いまの作りによるもの

- 保存はレコード 1 件ごとに確定し、ロールバックしません (上の「保存」)
- 楽観ロックは先に確かめるだけで、確かめてから書くまでの間の更新は防げません
- ExecuteSqlField の SQL 文・QueryField などの SQL を直接書く機能は使えません (ExecuteSqlField は拡張 SQL の呼び出しだけ)
- コメントは読むと JSON の文字で、書くと 1 件足すだけです (上の「コメント」)
- 選択肢はメタ情報の更新のときに取り込むだけです。画面の候補は Enum の定義から出します
- サイトの定義はメタ情報のファイルから読みます。プリザンターでサイトの設定を変えたら、デザイナでメタ情報を更新してデプロイしてください
- 列どうしの比較・JSON の列のノードでの検索・意味検索のようなフィールド独自の検索条件は使えません
- コネクターが絞る・並べる・集計するときに読むレコードの件数は `MaxRows` までです
- コネクターが並べるときの空欄・文字の扱いは、プリザンターの並びと違うことがあります
- SQL Server・MySQL のプリザンターでは、文字の比較 (大文字・小文字など) の結果が上に書いたものと違うことがあります (確かめていません)
